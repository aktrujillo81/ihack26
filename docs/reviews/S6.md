**Step proposed:** on branch `docs/s6-contracts` (docs only), Backend rewrites `docs/contracts.md`. Security, Phone / AI Prompter, Frontend and UX review it. A human merges.

**Sections of the contract:** (1) the Vapi payload as received, (2) `POST /api/vapi/webhook` for D3, (3) the common report format, (4) tables and the schema changes still needed, (5) rules, (6) the web API for D6, D7 and W5, (7) permissions, (8) configuration keys, (9) unknowns.

### Positions
- **P1 Find by name.** The extracted fields are read only from the entry of `message.artifact.structuredOutputs` whose `name` is `water_point_report` (search the values; never use the ID key). `message.analysis` and `message.summary` are never read. Exactly one matching entry with an object `result` is required. A missing key (calls 1 and 2), no match, or several matches: every field is `unknown` and the report is stored with `needs_review`.
- **P2 Allowlist.** The server reads only: `message.type`, `message.call.id`, `message.endedReason`, `message.artifact.transcript` (fallback `message.transcript`), and the nine fields. Nothing else is read, stored or logged. The raw body is never stored. The capture route is removed when D3 lands.
- **P3 Repeat deliveries.** `message.call.id` is stored only as a SHA-256 hash (`provider_call_ref`), unique per organization, used only to recognise the same call arriving twice (the second is answered 200 and not stored again). No API returns it.
- **P4 Transcript.** Stored, because DB-2 shows it. Before saving, phone-shaped digit runs are replaced by a fixed marker in the transcript, `location_text` and `summary`. Names cannot be removed reliably: this is written down as a remaining risk. Transcripts are returned only by the complaint detail endpoint, to signed-in users in scope. Retention is unknown (humans).
- **P5 Normalizing.** `people_affected` ("150" or "unknown") becomes an integer or null. `serves_school_or_clinic` ("true", "false", "unknown") becomes a boolean or null. `caller_confirmed` is a boolean. Enum fields outside the allowed values, and missing fields, become `unknown` and set `needs_review`. A missing or `unknown` location is stored as the text `unknown`, flagged `needs_review`, and creates no water point. No NOT NULL column has to become nullable.
- **P6 Review reasons.** One stored reason per report from a fixed list (draft: `malformed_payload`, `no_structured_data`, `unusable_location`, `ambiguous_match`, `incomplete_report`, `not_confirmed`). Backend sets the list and the order. UX words them. A caller's own "unknown" answer alone never sets `needs_review` (spec section 7).
- **P7 Organization and region of a call.** Taken from one `configuration` row with key `intake.phone`, created by the seed. Exactly one such row must exist. Otherwise the endpoint answers 503, stores nothing and logs a fixed code. Mapping several phone lines is future work.
- **P8 Responses.** 401 with an empty body (missing or wrong secret, or secret unset). 413 over the size limit. 200 `{ "ok": true }` for everything that was stored or ignored on purpose (other event types, a repeat delivery). 500 or 503 `{ "ok": false }` only when nothing could be stored. What Vapi does after a non-200 is unknown.
- **P9 API JSON.** camelCase names. Unknown people and school values are the string `"unknown"` in the API (null in the database), as `lib/domain/types.ts` already has. Timestamps are ISO 8601 UTC ending in `Z`. Lists never carry transcripts. A missing record and one outside the user's scope give the same 404 body.
- **P10 Schema changes are listed, not made.** The contract lists what `lib/db/schema.ts` still needs (draft: `reports.provider_call_ref`, `reports.needs_review_reason`, `reports.ended_reason`, candidate water points for a report, and the most-severe `problem`, `people_affected`, `serves_school_or_clinic`, `duration` on `complaints`). The task that needs each change makes it (D3, D4, D5), one migration at a time.
- **P11 Rules.** Values from spec section 7 stay as they are and live in `configuration`. The contract adds what the spec leaves open: the matching rule (deterministic: normalized location text equal within the same organization and region, and a compatible type; it may create a duplicate unverified point, which a responder merges), what "most severe" means, the score reason as one string built by the server, and the status changes allowed (open to passed_on or fixed, passed_on to fixed, fixed to open).
- **P12 Unknowns.** Anything the payload did not show is in an unknowns table with an owner and how to answer it: hang-up halfway, silence, no village, whether the end-call phrase cuts off words, Vapi retention, retries, other event types, billing rounding.
- **P13 No phone-like text.** The contract holds no phone-shaped text and no real IDs. Examples use the placeholders from the sample.

### Notes folded into the build brief
- **Security (wins on privacy):** call ID stored only as HMAC-SHA-256 with a server-only key, null when missing, never returned or logged. Scrub any run of 7 or more digits (with or without separators) from transcript, `location_text` and `summary`. **D3 stores a null transcript until the humans rule on red line 3 versus spec section 10.** `ended_reason` stored only as a seen value or `other`. Log fixed codes only. Secret checked before the body is read; failed-secret attempts rate-limited per client IP (429). A repeat and a first delivery answer identically. Organization and region never come from the request. Humans delete the raw captures on every machine when the capture route goes.
- **Backend (wins on data and API):** report committed first, then matching and scoring in a second transaction (`processing_error` on failure). Only `malformed_payload`, `no_structured_data`, `unusable_location`, `ambiguous_match`, `processing_error` leave a report unattached; other flagged reports still match and score. Accept strings or JSON numbers and booleans; missing `caller_confirmed` is null, never false. Schema list adds a partial unique index on the call reference, one active complaint per water point, `water_points.location_key`, candidates as a scoped join table. Exact matching rule and a total order for "most severe". 409 for stale or conflicting status changes. Keep the API names `lib/domain/types.ts` already uses, with a column-to-API table.
- **Phone / AI Prompter:** a null or non-object `result` takes the missing-data path; a leftover duplicate output name would make every report `unknown`. Trim and lowercase before checking. Mark observed versus configured values. More untested cases for the unknowns table. `docs/vapi-prompt.md` needs a follow-up (stale "unknown" lines, version table, Server URL row when D3 lands).
- **Frontend:** in-scope report detail read with transcript; reason is non-null whenever `needsReview` is true; one error body and codes; the D7 polling endpoint, list envelopes, sort orders and list cap; latitude and longitude as JSON numbers; pass-on request field; pin color source.
- **UX:** the API returns reason codes, never wording; score reason from fixed vocabulary with points and no caller text; list fields for DB-1 plus a total; identical 404 for reads, writes and notes, 403 for an in-scope Viewer write; last-report response with server time and the stale threshold; `summary` on detail only; marker text `[number removed]`.
